# 推拉结合的 Timeline Feed 流架构设计

## 1. 背景与问题
在社交平台（如 TikTok、微博、朋友圈）中，Feed 流通常分为两类：
1. **推荐页 (Recommend Feed)**：系统通过推荐算法将全站热门或用户可能感兴趣的视频推送到首页。
2. **关注页 (Follow/Timeline Feed)**：按时间线（Timeline）严格倒序展示用户关注的人发布的视频。

对于**关注页 Feed 流**，如何高效地分发和获取数据，是系统架构设计中的经典难题。

## 2. 传统方案与痛点

### 2.1 读扩散 (Pull 模式)
**原理**：用户发布视频时，只写入自己的发件箱（Outbox）和数据库。当粉丝刷新关注页时，系统实时去拉取该粉丝关注的所有人的发件箱，在内存中按时间进行合并排序（Merge Sort），然后返回。
* **优点**：写入极快，发布视频几乎 0 延迟；节省存储空间，一份视频只存一次。
* **缺点**：读取极慢！如果一个用户关注了 1000 个人，刷新一次 Feed 流就需要并发读取 1000 个人的发件箱并做内存聚合。在晚高峰时，读请求会瞬间压垮数据库或缓存。

### 2.2 写扩散 (Push 模式)
**原理**：用户发布视频时，系统遍历该用户的所有粉丝，将该视频的 ID 写入每一个粉丝的收件箱（Inbox）中。当粉丝刷新关注页时，只需要读取自己唯一的收件箱即可。
* **优点**：读取极快，逻辑简单，粉丝刷新时直接从 Redis ZSet 返回自己的 Timeline。
* **缺点**：写入极慢且极耗空间！如果一个“大V”有 1000 万粉丝，发一个视频需要写入 1000 万次 Redis。这会产生巨大的写入延迟（“大V发视频，粉丝半天刷不出来”）和存储浪费。

## 3. 破局之道：推拉结合 (Push-Pull 混合模式)

为了兼顾“大V”和“普通用户”的极端场景，工业界通常采用 **“推拉结合（Push & Pull）”** 的架构。

### 3.1 核心策略
我们通过**粉丝数量**（例如：1 万粉丝）作为阈值，将用户分为两类：
1. **普通用户（活跃数高，粉丝少）** -> 采用 **Push（写扩散）**
2. **大V/头部创作者（活跃数低，粉丝极多）** -> 采用 **Pull（读扩散）**

### 3.2 详细流程

#### 场景一：发布视频 (Publish)
* **当普通用户发布视频时**：
  将视频 ID 写入自己的 Outbox。同时，触发异步 Worker，遍历其所有粉丝，将视频 ID **Push** 到粉丝的 Inbox 中（ZSet，按时间戳 Score）。
* **当大V发布视频时**：
  仅仅将视频 ID 写入自己的 Outbox（ZSet），**绝不执行 Push 操作**。

#### 场景二：刷新关注页 (Get Follow Feed)
当用户打开关注页刷新时，系统需要做两件事并进行合并：
1. **读 Inbox (Push 侧)**：直接从自己的 Inbox 中获取普通用户发布并推送过来的视频 ID。
2. **读大V Outbox (Pull 侧)**：获取自己关注列表中的“大V”名单，并发读取这些大V的 Outbox。
3. **合并与排序**：将 Inbox 的结果与各大V Outbox 的结果在内存中进行合并，按时间倒序截取一页（如 30 条），返回给客户端。

## 4. 本项目实践细节

我们在本项目中通过 Redis 实现了这套推拉结合架构：

### 4.1 数据结构
* **发件箱 (Outbox)**: `ZSET user:outbox:{userID}`，Score 为发布时间戳。
* **收件箱 (Inbox)**: `ZSET user:inbox:{userID}`，Score 为发布时间戳。
* **容量控制**: 为了防止 BigKey，发件箱和收件箱均使用 `ZREMRANGEBYRANK` 限制最大长度（例如 1000 条），因为用户极少会刷到 1000 条以前的动态。

### 4.2 代码实现位置
* **写入侧**: `internal/content/service/video.go` 的 `PublishVideo` 方法中。通过 Goroutine 异步判断粉丝数，粉丝数 $< 10000$ 走 Inbox Push，同时所有发布都记录 Outbox。
* **读取侧**: `internal/content/service/video.go` 的 `GetFollowFeed` 方法中。并发拉取当前用户的 Inbox 和其关注的大V的 Outbox，在内存中执行排序合并后批量回表查询视频详情。

## 5. 总结
推拉结合模型（Timeline）完美平衡了读写放大问题。对于占大盘 99% 的普通用户，通过 Push 保证了极致的拉取体验；对于 1% 的大V，通过 Pull 避免了系统的写入雪崩。结合 Redis ZSet 和游标分页，构成了现代短视频/社交平台高可用架构的核心基石。
